**Tier reason:** Transactions over several tables with row locks (D1); a data migration

Work from the brief: `node scripts/pm4.mjs brief T-0060`. Verify with `node scripts/pm4.mjs check T-0060`.

## Implementation notes
_Implementer: what changed, and anything the reviewer should look at._

- `ProjectsRepository.delete` / `TasksRepository.delete`: one transaction each, as in *Interfaces*: row locks with
  `FOR UPDATE`, retained names written onto the caller's logs, then the `DELETE` (the FKs cascade tasks and null the
  log links). `ProjectsRepository.delete` locks the project's tasks first, then the project (D1): the same order a
  concurrent log insert's FK checks take, so the two don't deadlock. The task lock is scoped by `userId` too.
- Repositories read and filter no `deletedAt` / `projectDeletedAt`; the only write paths for removal are `delete`.
- Services: `remove` → `404 not-found` for a non-UUID or a row that isn't the caller's; `findOwned(userId, id)` takes
  no `opts`; the controllers expose `DELETE /projects/{id}` and `DELETE /tasks/{id}` (`204`). Tasks create/update call
  `projectsService.findOwned` directly. Task `project.deleted` is always `false`.
- Schema: plain indexes `projects_user_id_idx`, `tasks_project_id_idx`, `tasks_user_id_status_idx`; the `deletedAt`
  column is still declared (T4 handles it). Migration `api/drizzle/0005_permanent_delete.sql` generated by
  `npm run db:generate -- --name permanent_delete`, with the data step prepended.
- AC-7 dry run on a scratch local database (`pm4_ac7`, migrations 0000–0004 applied via psql, then 0005; the scratch database was deleted afterwards):
  P, its task and U were absent; P's direct log had `deleted_project_title = P`, its task's log `PT`/`P`; `\d projects`
  showed `projects_user_id_idx` only. The owner still verifies AC-7.
- Unit specs in `src/projects`, `src/tasks` cover `delete` / `remove` and `findOwned`.
- `api/openapi.json` re-exported (matches the current endpoints and delete summaries).
