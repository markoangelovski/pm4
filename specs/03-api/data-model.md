# Data Model

## Purpose
The logical and physical data model for Neon Postgres (Drizzle). Also defines the **storage rules**,
because the database has a fixed storage quota: **0.5 GB** on the Neon free tier (OQ-008, OQ-032).

## Entity relationships

```
users 1──* user_identities            (provider, subject) → user
users 1──* projects 1──* tasks
users 1──* workdays                   PK (user_id, work_date)
users 1──* time_logs *──0..1 tasks    (FK ON DELETE SET NULL)
                     *──0..1 projects (FK ON DELETE SET NULL)
```

## Storage rules (apply to every table)
1. **Smallest correct type:** `date` (4 B) for calendar dates, `smallint` (2 B) for durations
   (minutes) and time of day, a Postgres **enum** (4 B) for fixed value sets, and `timestamptz` (8 B) only for real instants.
2. **Bounded text:** `varchar(n)` with the limits below. In Postgres, `varchar(n)` has the same storage
   as `text`, but it enforces the limit. Short values (< 127 B) carry a 1-byte header. Never use `char(n)`.
3. **No stored derived data:** counts and totals are computed by queries (legacy stored task counters on projects. Don't).
4. **No unused columns:** every column must be required by a spec. Nullable columns cost nothing when NULL (null bitmap).
5. **Natural composite keys** where a row is identified by them (`workdays`, `user_identities`), with no extra surrogate id.
6. **Lean indexes:** only indexes that serve a documented query or an FK used for deletes. Use partial
   indexes (`WHERE deleted_at IS NULL`) where lists filter on them.
7. **Column order:** declare 8-byte columns (`timestamptz`) first, then 4-byte (`date`, enum), then
   2-byte (`smallint`), then `uuid`/`varchar`, to minimize alignment padding.
8. **Neon history counts toward storage:** avoid chatty writes. No autosave per keystroke, no "last seen" updates, no write-on-read (legacy auto-created Day rows on read. Don't).
9. **No timestamps without a use:** `time_logs` has no `created_at`/`updated_at`. The order within a day is `position`, and UUIDv7 ids are time-ordered anyway.
10. **Derive, don't store:** log clock times come from the workday start + preceding durations (OQ-036), so they aren't stored.

## Tables (proposed)
All primary keys are **UUIDv7** in `uuid` columns (OQ-027), generated by the database default `uuidv7()` (Postgres 18, OQ-042).

### users
| Column | Type | Constraints |
| --- | --- | --- |
| created_at, updated_at | timestamptz | not null, default now() |
| id | uuid | PK, default `uuidv7()` (Postgres 18) |
| email | varchar(254) | not null, unique (lower(email)) |
| display_name | varchar(100) | not null |
| avatar_url | varchar(500) | null |
| time_zone | varchar(64) | not null, IANA name. Set from the browser zone at first sign-in (FR-AUTH-006) |

### user_identities
| Column | Type | Constraints |
| --- | --- | --- |
| created_at | timestamptz | not null |
| provider | enum `auth_provider` (`google`) | PK part |
| subject | varchar(255) | PK part (provider's user id, e.g. Google `sub`) |
| user_id | uuid | FK → users ON DELETE CASCADE, indexed |

### projects
| Column | Type | Constraints |
| --- | --- | --- |
| created_at, updated_at | timestamptz | not null |
| deleted_at | timestamptz | null = active |
| id | uuid | PK |
| user_id | uuid | FK → users ON DELETE CASCADE |
| title | varchar(200) | not null |
| description | varchar(2000) | null |
| project_lead | varchar(100) | null |

Indexes: `(user_id) WHERE deleted_at IS NULL`, `(user_id, deleted_at) WHERE deleted_at IS NOT NULL` (trash/purge).

### tasks
| Column | Type | Constraints |
| --- | --- | --- |
| created_at, updated_at | timestamptz | not null |
| deleted_at | timestamptz | null = not individually deleted |
| due_date | date | null? (OQ-028) |
| status | enum `task_status` (`upcoming`,`in-progress`,`completed`) | not null, default `upcoming` |
| id | uuid | PK |
| user_id | uuid | FK → users ON DELETE CASCADE |
| project_id | uuid | FK → projects ON DELETE CASCADE |
| title | varchar(200) | not null |
| description | varchar(2000) | null |
| project_lead | varchar(100) | null? (OQ-028) |
| external_link | varchar(500) | null, http(s) URL |

Indexes: `(project_id) WHERE deleted_at IS NULL`, `(user_id, status) WHERE deleted_at IS NULL`, `(user_id, deleted_at) WHERE deleted_at IS NOT NULL`.
A task is **effectively deleted** if `tasks.deleted_at IS NOT NULL` **or** its project's `deleted_at IS NOT NULL`.

### workdays
| Column | Type | Constraints |
| --- | --- | --- |
| work_date | date | PK part |
| start_minute | smallint | null, 0–1439 |
| user_id | uuid | PK part, FK → users ON DELETE CASCADE |

A row exists only when a start time is set (OQ-021). ~26 B of data per row.

### time_logs
One row per logged block of work (req-time-logs §Model).

| Column | Type | Constraints |
| --- | --- | --- |
| work_date | date | not null |
| position | smallint | not null, ≥ 1, unique per (user_id, work_date) (deferrable) |
| duration_minutes | smallint | not null, 1–max (OQ-035) |
| id | uuid | PK (v7) |
| user_id | uuid | FK → users ON DELETE CASCADE |
| task_id | uuid | null, FK → tasks **ON DELETE SET NULL** |
| project_id | uuid | null, FK → projects **ON DELETE SET NULL** |
| note | varchar(1000) | not null, trimmed, length ≥ 1 (OQ-008) |
| deleted_task_title | varchar(200) | null, set only when the linked task is purged |
| deleted_project_title | varchar(200) | null, set only when the linked project is purged |

Invariants:
- If `task_id` is set, `project_id` = that task's `project_id`. The service maintains this, including when a task moves to another project (one `UPDATE … WHERE task_id = …`).
- Project-only link: `task_id` null, `project_id` set. Unlinked logs (if allowed, OQ-020): both null.
- Positions are dense (1…n) per user and day. Append = max + 1. Reorder, insert and delete renumber
  that day's logs in one transaction (a few rows at most).

Indexes: `UNIQUE (user_id, work_date, position)` (day view, ordering, and range scans for reports),
`(task_id) WHERE task_id IS NOT NULL`, `(project_id) WHERE project_id IS NOT NULL` (task/project views, and FK SET NULL on purge).

## Retained names (FR-TRASH-006)
- **While trashed:** the FK still points to the row. The API returns `{id, title, deleted: true}` via a join.
- **On purge/permanent delete** (in one transaction): first
  `UPDATE time_logs SET deleted_task_title = t.title WHERE task_id = …` (and the same for projects,
  including the tasks of a purged project), then delete. The FKs then set `task_id`/`project_id` to NULL.
- Read model: `task = task_id ? {id, title, deleted} : deleted_task_title ? {id: null, title: deleted_task_title, deleted: true} : null`.
  The snapshot columns cost nothing until a purge happens.
- Reports group purged projects by `deleted_project_title` (OQ-029b).

## Storage budget (estimate)
Row ≈ 24 B header + data + 4 B line pointer, plus index entries (~32–40 B per uuid-based index entry).

| Table | ~Data/row | Indexes/row | ~Total/row |
| --- | --- | --- | --- |
| time_logs (avg note 80 chars, linked) | 175 B | pkey + (user, date, pos) + task + project ≈ 140 B | ~320 B |

A heavy user who switches often (20 logs/day, 250 days/yr) ≈ 5,000 logs ≈ **1.6 MB/yr**, or ~2.5 MB/yr
with bloat and history overhead. **0.5 GB ≈ 200 user-years.** Dropping the legacy event level saves a
row and ~4 index entries per block. Keys are UUIDv7 (16 B, OQ-027).

## Migrations
drizzle-kit generates SQL migrations into `api/drizzle/`, which are committed and reviewed. They run
explicitly in CI against the direct URL (ADR-0008). They must be expand/contract compatible, because
there's no staging.
