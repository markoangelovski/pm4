# Data Model

## Purpose
The logical and physical data model for Neon Postgres (Drizzle). Also defines the **storage rules**,
because the database has a fixed storage quota: **0.5 GB** on the Neon free tier (OQ-008, OQ-032).

## Entity relationships

```
users 1──* user_identities            (provider, subject) → user
users 1──* projects 1──* tasks       (FK ON DELETE CASCADE)
users 1──* workdays                   PK (user_id, work_date)
users 1──* time_logs *──0..1 tasks    (FK ON DELETE SET NULL)
                     *──0..1 projects (FK ON DELETE SET NULL)
```

Deletes are **permanent** (hard deletes). Every user-owned table references
`users` with `ON DELETE CASCADE`, so deleting a user removes all of that user's data (identities, projects,
tasks, workdays, time logs, bookings, settings and integration connections); the API also removes the user's
Redis sessions. A project or task of another user whose lead was the deleted user keeps the saved lead name
(`project_lead_user_id ON DELETE SET NULL`, *Project lead* below). This is a data rule only: there's no account
deletion in the UI or the API (req-auth). Deleting a project deletes its tasks (`tasks.project_id ON DELETE CASCADE`). Time logs are never
deleted with their task or project: they keep its name (*Retained names* below).

## Storage rules (apply to every table)
1. **Smallest correct type:** `date` (4 B) for calendar dates, `smallint` (2 B) for durations
   (minutes) and time of day, a Postgres **enum** (4 B) for fixed value sets, and `timestamptz` (8 B) only for real instants.
2. **Bounded text:** `varchar(n)` with the limits below. In Postgres, `varchar(n)` has the same storage
   as `text`, but it enforces the limit. Short values (< 127 B) carry a 1-byte header. Never use `char(n)`.
3. **No stored derived data:** counts and totals are computed by queries (legacy stored task counters on projects. Don't).
4. **No unused columns:** every column must be required by a spec. Nullable columns cost nothing when NULL (null bitmap).
5. **Natural composite keys** where a row is identified by them (`workdays`, `user_identities`), with no extra surrogate id.
6. **Lean indexes:** only indexes that serve a documented query or an FK used for deletes. Use partial
   indexes (`WHERE … IS NOT NULL`) for sparse columns.
7. **Column order:** declare 8-byte columns (`timestamptz`) first, then 4-byte (`date`, enum), then
   2-byte (`smallint`), then `uuid`/`varchar`, to minimize alignment padding.
8. **Neon history counts toward storage:** avoid chatty writes. No autosave per keystroke, no "last seen" updates, no write-on-read (legacy auto-created Day rows on read. Don't).
9. **No timestamps without a use:** `time_logs` has no `created_at`/`updated_at`. Logs are shown in entry order, which the time-ordered UUIDv7 id already gives.
10. **Derive, don't store:** day and project totals, and the header's *start + logged*, are computed by queries.

## Tables (proposed)
All primary keys are **UUIDv7** in `uuid` columns (OQ-027), generated by the database default `uuidv7()` (Postgres 18, OQ-042).

### users
| Column | Type | Constraints |
| --- | --- | --- |
| created_at, updated_at | timestamptz | not null, default now() |
| id | uuid | PK, default `uuidv7()` (Postgres 18) |
| email | varchar(254) | not null, unique (lower(email)) |
| display_name | varchar(100) | not null |
| avatar_url | varchar(500) | null |
| time_zone | varchar(64) | not null, IANA name. Set from the browser zone at first sign-in (FR-AUTH-006) |
| daily_target_minutes | smallint | not null, default 420, 15–1440, a multiple of 15 (FR-TLOG-017, OQ-115) |

### user_identities
| Column | Type | Constraints |
| --- | --- | --- |
| created_at | timestamptz | not null |
| provider | enum `auth_provider` (`google`) | PK part |
| subject | varchar(255) | PK part (provider's user id, e.g. Google `sub`) |
| user_id | uuid | FK → users ON DELETE CASCADE, indexed |

### projects
| Column | Type | Constraints |
| --- | --- | --- |
| created_at, updated_at | timestamptz | not null, default now() |
| id | uuid | PK, default `uuidv7()` |
| user_id | uuid | not null, FK → users ON DELETE CASCADE |
| project_lead_user_id | uuid | null, FK → users ON DELETE SET NULL. Set = a **user lead** (OQ-076) |
| title | varchar(200) | not null |
| description | varchar(2000) | null |
| external_link | varchar(500) | null, http(s) URL (OQ-079) |
| project_lead | varchar(100) | null. The **text lead**; with a user lead, the user's name when it was saved (the fallback, OQ-077) |

Indexes: `(user_id)`.
`project_lead_user_id` has no index: there's no account deletion in the UI, so the FK action practically never runs.
`updated_at` changes only when the project's own fields change, never because of its tasks (OQ-091).

### Project lead (projects and tasks)
Two columns hold the lead (OQ-076, OQ-077). The read model:
- `project_lead_user_id` set → **user lead**: the referenced user's **current** `display_name` and `avatar_url` (join).
- else `project_lead` set → **text lead**: that text. This also covers a user lead whose account was deleted (the FK set the id to NULL; the saved name stays).
- else no lead.

Writes: a user lead stores the id **and** the user's `display_name` at save time in `project_lead`; a text lead stores the text and NULL id; no lead stores two NULLs.
The lead user may be any registered user, not only the owner (security.md *Authorization*).

### tasks
| Column | Type | Constraints |
| --- | --- | --- |
| created_at, updated_at | timestamptz | not null, default now() |
| due_date | date | null (OQ-028) |
| status | enum `task_status` (`upcoming`,`in-progress`,`completed`) | not null, default `upcoming` |
| id | uuid | PK, default `uuidv7()` |
| user_id | uuid | not null, FK → users ON DELETE CASCADE |
| project_id | uuid | not null, FK → projects ON DELETE CASCADE |
| project_lead_user_id | uuid | null, FK → users ON DELETE SET NULL (as projects) |
| title | varchar(200) | not null |
| description | varchar(2000) | null |
| external_link | varchar(500) | null, http(s) URL |
| project_lead | varchar(100) | null (as projects) |

Indexes: `(project_id)` (project task list and counts, and the cascade when a project is deleted), `(user_id, status)` (cross-project list).
`updated_at` changes on every edit, including a status change (OQ-087) and a move to another project.

### workdays
| Column | Type | Constraints |
| --- | --- | --- |
| work_date | date | PK part |
| start_minute | smallint | not null, 0–1425, a multiple of 15 |
| user_id | uuid | PK part, FK → users ON DELETE CASCADE |

A row exists as soon as a date has a start time, which is set with the date's first log (FR-TLOG-009). Deleting
the day's logs does not delete the row. ~26 B of data per row.

### time_logs
One row per logged block of work (req-time-logs §Model).

| Column | Type | Constraints |
| --- | --- | --- |
| work_date | date | not null, not in the future (checked by the service, in the user's zone) |
| booking_date | date | null = not booked; not in the future (checked by the service); set only on a bookable log (FR-BOOK-004, OQ-123) |
| duration_minutes | smallint | not null, 15–1440, a multiple of 15 |
| exclude_from_stats | boolean | not null, default false (FR-TLOG-018) |
| id | uuid | PK (v7) |
| user_id | uuid | FK → users ON DELETE CASCADE |
| task_id | uuid | null, FK → tasks **ON DELETE SET NULL** |
| project_id | uuid | null, FK → projects **ON DELETE SET NULL** |
| text | varchar(1000) | not null, trimmed, length ≥ 1 |
| title | varchar(100) | null, trimmed, length ≥ 1 when set |
| deleted_task_title | varchar(200) | null, set only when the linked task is deleted |
| deleted_project_title | varchar(200) | null, set only when the linked project is deleted |

Invariants:
- If `task_id` is set, `project_id` = that task's `project_id`. The service maintains this, including when a task moves to another project (one `UPDATE time_logs SET project_id = … WHERE task_id = …`, added to API-TSK-004 by feat-tlog-api).
- Project-only link: `task_id` null, `project_id` set. Unlinked (*unsorted*) logs: both null.
- A project's logged time is `SUM(duration_minutes) WHERE project_id = …`, which covers its direct logs and its tasks' logs.
- A day's logs are read in `id` order (entry order).
- `booking_date` is set only while the log is bookable: `exclude_from_stats` false and a project (`project_id` or `deleted_project_title`). An update that makes the log unbookable sets it to null in the same `UPDATE` (FR-BOOK-006).

Indexes: `(user_id, work_date, id)` (day view, calendar marks), `(task_id) WHERE task_id IS NOT NULL`,
`(project_id) WHERE project_id IS NOT NULL` (task/project sections and totals, and FK SET NULL on delete),
`(user_id, booking_date) WHERE booking_date IS NOT NULL` (the Bookings range: logs booked into it from outside it, API-BOOK-001).

## Retained names (FR-TLOG-014)
- **On delete** (in one transaction): first save the names on the linked logs, then delete the row. The FKs
  then set `task_id`/`project_id` to NULL.
  - Deleting a task: `UPDATE time_logs SET deleted_task_title = t.title WHERE task_id = …`. The log keeps its
    `project_id` (the project still exists).
  - Deleting a project: `UPDATE time_logs SET deleted_project_title = p.title WHERE project_id = …`, and
    `deleted_task_title = t.title` for the logs of its tasks. The cascade then deletes the tasks.
- Replacing a log's link (`taskId` or `projectId` in API-TLOG-004) sets both `deleted_task_title` and
  `deleted_project_title` to null in the same `UPDATE`: the retained names describe the deleted link, not the new one.
- Read model: `task = task_id ? {id, title, deleted: false} : deleted_task_title ? {id: null, title: deleted_task_title, deleted: true} : null`
  (the same for `project`). The snapshot columns cost nothing until a delete happens.
- Reports group deleted projects by `deleted_project_title` (OQ-029b).

## Storage budget (estimate)
Row ≈ 24 B header + data + 4 B line pointer, plus index entries (~32–40 B per uuid-based index entry).

| Table | ~Data/row | Indexes/row | ~Total/row |
| --- | --- | --- | --- |
| time_logs (avg text 80 chars, linked, booked) | 179 B | pkey + (user, date, id) + task + project + (user, booking date) ≈ 170 B | ~355 B |

A heavy user who switches often (20 logs/day, 250 days/yr) ≈ 5,000 logs ≈ **1.8 MB/yr**, or ~2.8 MB/yr
with bloat and history overhead. **0.5 GB ≈ 180 user-years.** Dropping the legacy event level saves a
row and ~4 index entries per block. Keys are UUIDv7 (16 B, OQ-027).

## Migrations
drizzle-kit generates SQL migrations into `api/drizzle/`, which are committed and reviewed. They run
explicitly in CI against the direct URL (ADR-0008). They must be expand/contract compatible, because
there's no staging.
